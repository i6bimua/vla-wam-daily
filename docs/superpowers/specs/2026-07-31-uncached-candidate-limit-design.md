# 未缓存候选论文上限设计

## 背景

2026-07-31 的三天回看任务在预筛后得到 76 篇候选论文，并因
`analysis.max_candidates: 60` 主动终止。代码在读取分析缓存之前检查全部候选数量，
因此已缓存、不会调用 DeepSeek 的论文也占用了 API 安全额度。

生产日志和代码路径共同确认了这一顺序：

1. 关键词预筛生成 `candidates`。
2. 立即检查 `len(candidates)`。
3. 之后才读取分析缓存并划分 `records` 与 `pending`。

这与“缓存避免重复模型调用、60 篇上限限制单次 DeepSeek 工作量”的目标不一致。

## 选定方案

把候选数量检查移动到缓存划分之后，并只检查 `pending`：

- `candidates` 保留全部通过预筛或被强制选择的论文。
- 命中当前模型和 prompt 版本缓存的论文进入 `records`，不占用上限。
- 未命中缓存的论文进入 `pending`，计入 60 篇上限。
- `--force-arxiv-id` 继续绕过缓存，因此强制重分析论文计入 `pending`。
- `stats.prefiltered` 继续报告全部预筛候选数。
- `stats.cache_hits` 和 `stats.model_calls` 继续分别报告缓存复用与实际模型调用。

错误信息明确使用 `uncached candidates`，避免把上限误解为网站能保存或展示的论文总数。

## 安全边界

若 `len(pending)` 超过 `analysis.max_candidates`，任务仍在创建任何 DeepSeek future、
请求 Figure 或写入数据之前抛出 `CandidateLimitError`。配置值继续保持 60，不扩大最大
API 调用量，不改变质量模型、发布阈值、三天回看、缓存键或持久化格式。

读取缓存发生在保护检查之前；若缓存文件损坏，现有严格加载行为继续使任务失败，不绕过
数据完整性保护。

## 备选方案

- 把上限提高到 100：能通过当前 76 篇候选，但扩大最坏情况下的 API 成本。
- 把自动回看改为 1 天：能减少候选数，但削弱临时失败和延迟收录后的补偿能力。

## 测试

1. 建立“总候选数超过上限，但只有一个未缓存候选”的回归场景；旧代码必须失败。
2. 修复后确认该场景成功，缓存论文不触发模型调用，未缓存论文只调用一次。
3. 保留“未缓存候选超过上限”的测试，确认模型、Figure 和磁盘写入均未发生。
4. 确认强制重分析绕过缓存并计入上限。
5. 运行完整 Python、静态检查、类型检查和前端构建。
6. 发布后用三天回看任务验证生产缓存能够解除错误阻塞。
